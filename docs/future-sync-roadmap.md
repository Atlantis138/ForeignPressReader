# 外刊阅读器未来同步功能开发路线

> 2026-09 后续实现：文章阅读记录、译文版本、增量投影、解析补全、启动恢复与 Android 原生媒体服务已追加到当前源码，详见 [v4 契约](reader-data-v4.md) 和 [修复记录](project-repair-2026-09.md)。旧阶段状态保留作为历史记录。

> 文档状态：正式同步设计基线（传输层推迟到 Android 本地 MVP/Beta 完成后）
> 适用范围：Electron/Windows、未来 Tauri/Android，以及后续可选的云端中继
> 最后更新：2026-07-15

## 1. 目的与边界

本路线图定义外刊阅读器从“手动导入/导出全量便携备份”演进到“本地优先、跨平台、局域网增量同步”的长期方向。后续 Codex 或开发者在移植 Android、增加局域网传输或调整备份格式时，应以本文的产品语义和数据契约为基线，不得直接复制正在使用的 SQLite 文件，也不得让平台 SDK 渗入 `src/core`。

Android 移植的主路线、阶段出口和当前环境见[外刊阅读器 Tauri Android 移植路线](tauri-android-port-roadmap.md)。本文件只负责同步语义与传输路线；同步不是首个 Android 原型的验收目标。

最终体验参考 LocalSend：两台或多台设备处于同一局域网并主动打开同步入口时，可以发现彼此；用户明确选择方向并确认后，发送端把变化数据和接收端缺失的刊物发送给接收端。系统不依赖账号或中心服务器，默认不在后台持续扫描网络。

以下内容不属于初始局域网同步目标：

- 自动双向同步、无冲突的实时协作或完整设备镜像。
- 后台常驻发现、未经用户确认的自动接收。
- 复制 SQLite、应用数据目录、缓存、词典索引、API 密钥或设备身份。
- 单篇文章物理删除。初期只同步整本刊物的生命周期；未来如需隐藏文章，应建立独立的文章可见性覆盖层。
- 把云服务作为本地阅读和学习功能的前置依赖。

## 2. 不可改变的产品语义

### 2.1 手动定向推送

一次同步是用户明确发起的 `A → B` 定向推送，而不是自动双向合并：

1. 对 A、B 中具有相同稳定 ID 的可变记录，A 的当前状态覆盖 B，即使 A 的 `updatedAt` 更早。
2. B 独有、A 从未拥有且没有对应删除墓碑的记录继续保留。“发送端没有这条记录”不等于“发送端要求删除”。
3. 删除只能由 A 携带的显式墓碑表达；墓碑必须像普通逻辑记录一样传播、去重和参与兼容判断。
4. 复习事件、强化事件等不可变事件按稳定事件 ID 取并集。相同 ID、相同内容是幂等重放；相同 ID、不同内容视为数据损坏并拒绝整个批次。
5. 发送端胜出只影响本批次裁决到的同 ID 逻辑记录，不把 B 完全克隆成 A。若未来需要“完全替换设备”，必须作为独立的高风险恢复操作设计。
6. 同一批次重复提交、响应丢失后重试或多次转发，不得生成重复记录或重复副作用。
7. 只有逻辑记录、所需大对象和数据库事务全部成功后才能确认批次并推进游标；失败必须保持可重试。

### 2.2 两种合并策略必须分离

便携备份与设备推送复用同一套稳定逻辑 DTO 和版本升级器，但使用不同策略：

| 使用场景 | 策略 | 规则 |
|---|---|---|
| 全量便携备份导入 | `NewerWins` | 可变记录按 `(updatedAt, deviceId)` 后写优先，适合恢复或汇总多个历史备份 |
| 局域网定向推送 | `IncomingWins` | 对本批次包含的同 ID 可变记录，无条件采用发送端状态 |
| 两种场景中的不可变事件 | `ImmutableUnion` | 按事件 ID 幂等并集；同 ID 内容冲突则拒绝 |

不得用现有备份的 `NewerWins` 实现设备推送，否则发送端较旧的明确选择无法覆盖接收端。也不得让 `IncomingWins` 改变普通备份导入的安全语义。

## 3. 数据分类与同步政策

所有跨平台字段使用稳定、显式、camelCase 的逻辑 DTO，不暴露 SQLite 列名、Node `Buffer`、本地路径或 Electron 类型。

| 数据 | 同步方式 | 便携备份 | 说明 |
|---|---|---|---|
| 规范化刊物内容包 | 以原始导入内容的完整 SHA-256 寻址，只传接收端缺失包 | 包含所有活动刊物 | 包含 `publication.json` 与实际资源，不包含原始 EPUB；接收端校验后直接恢复 parsed-only 书库 |
| 刊物存在/删除状态 | 可变生命周期记录，删除使用显式墓碑 | 包含 | 初期粒度为整本刊物 |
| 阅读位置 | 可变记录 | 包含 | 使用稳定块/词元锚点；像素滚动值仅作设备本地回退 |
| 用户词汇、来源、收藏语境 | 可变记录及取消墓碑 | 包含 | 按稳定 ID 裁决 |
| 学习计划、成员、逐词排除、FSRS 配置 | 可变记录及墓碑 | 包含 | 重置操作必须阻止旧进度复活 |
| 复习卡当前状态 | 可变快照 | 包含 | PeerPush 由发送端当前卡片覆盖 |
| 复习、强化等历史事件 | 不可变事件并集 | 包含 | 事件 ID 必须稳定且可校验 |
| 全局/逐词暂停与进度重置 | 可变记录或显式墓碑 | 包含 | 早于重置点的旧卡片、事件不得复活 |
| 分类、自定义刊名、归类关系 | 细粒度可变记录 | 包含 | 不长期依赖一个巨大的 `library.management` JSON 作为冲突单位 |
| 跨平台阅读外观 | 逻辑设置投影 | 包含完整本机设置 | 同步主题、字号、行距、纸张暖度；栏宽等设备布局保留接收端值 |
| 跨平台语音偏好 | 逻辑设置投影 | 包含完整本机设置 | 同步语言、语速、自动发音；系统声音 ID 保留接收端值 |
| 翻译、词典、学习偏好 | 逻辑设置投影 | 包含 | 只同步不含密钥的逻辑值 |
| 书库视图、排序、当前筛选 | 设备本地 | 可随完整备份恢复 | 不参与设备推送 |
| 翻译和文中义缓存 | 不同步 | 排除 | 可重新生成 |
| ECDICT 索引 | 不同步 | 排除 | 可重新安装 |
| 活动学习 session、临时队列 | 不同步 | 排除 | 属于瞬时运行状态；收到计划删除或进度重置后必须在本机事务内清理失效项并结束空 session |
| 刊物正文引用的图片等资源 | 随规范化刊物包同步 | 随刊物包包含 | 无源 EPUB 时属于书库必要内容，不归入缓存 |
| 缩略图、翻译、网络与其他缓存 | 不同步 | 排除 | 可重新生成 |
| SQLite 文件、WAL、迁移快照 | 永不复制 | 排除 | 各平台通过逻辑模型和顺序迁移维护自己的数据库 |
| API 密钥、TLS 私钥、设备 ID、信任关系和同步游标 | 永不同步 | 排除 | 必须由每台设备独立生成并安全保存 |

## 4. 平台无关的同步内核

### 4.1 内容寻址的规范化刊物包

规范化 `.fprpub` 刊物包是初期唯一需要传输的大对象。原始 EPUB 只在用户发起导入时暂存和解析，不进入书库、备份或新同步批次：

1. 发送端先在逻辑批次中声明刊物状态、原始内容 SHA-256、格式 ID、刊物包 payload SHA-256 和字节大小。
2. 接收端在摘要响应中返回已拥有的原始内容哈希。
3. 发送端从本机规范化数据库与 `assets/` 临时生成缺失哈希对应的 `.fprpub`；包内只有版本化清单、`publication.json` 和资源。
4. 接收端将包写入 staging，同时校验外层 payload 哈希、内层逐文件哈希、路径、内容 ID 版本、计划身份和资源引用，再直接恢复统一领域模型。
5. 导入失败时不提交逻辑批次，并清理本批次 staging 与新生成的孤立数据；成功后也不保留临时包。
6. 刊物被删除后保留生命周期墓碑，不在活动书库、便携备份或后续同步批次中继续携带内容包；同一刊物以后重新导入时写入新的 `present` 状态。

### 4.2 合并式 revision 索引

同步内核采用“当前状态 + 合并式变化索引”，不永久保存每一次完整操作事件：

- 本设备维护单调递增的 `revision`。
- `(entityType, entityKey)` 只保留最近一次变化的 revision；同一实体连续修改会合并为一个待同步实体引用。
- 逻辑数据写入与 revision 登记必须处于同一个 SQLite 事务，避免数据已变但索引未变。
- 生成批次时根据实体引用读取发送端的当前逻辑状态，而不是转发可能过时的历史操作。
- 接收远端数据后，如果本地状态确实改变，也登记新的本地 revision，使变化可以经 B 继续传播给 C；内容完全相同的重放不制造新 revision。
- 每个已配对设备保存已确认的发送 revision、已应用的接收 revision 和对方最后检查到的本地 revision。
- 按 `(senderDeviceId, batchId)` 保存批次回执及 payload hash；同批次不同 payload 必须拒绝。
- 只有所有仍受信任的设备都确认后才能压缩旧 revision 信息；若所需历史已经被压缩，自动回退到逻辑快照协商。

### 4.3 首次快照与后续增量

首次建立对等关系时没有可信游标，因此使用逻辑快照：发送端枚举所有当前可同步逻辑记录和仍需保留的墓碑，但仍只传接收端缺失的规范化刊物包。逻辑快照不等于覆盖接收端独有数据。

后续 `A → B` 的增量协商流程：

1. B 返回协议/模型版本、自己已成功应用的 A revision、A 上次检查 B 之后由 B 改变的实体引用，以及 B 已有的刊物内容哈希。
2. A 取两组实体引用的并集：B 尚未确认的 A 端变化，以及 B 新改变、需要由 A 重新裁决的实体。
3. A 为每个引用读取自己的当前状态。A 拥有记录或显式墓碑时将其加入批次；A 从未拥有该实体时不凭“缺席”生成删除。
4. B 在应用前完成版本、大小、哈希、稳定 ID、父子依赖和不可变事件冲突校验，并展示新增、更新、删除数量及传输大小预览。
5. B 按依赖顺序应用父记录、可变状态、事件和重置，最后执行刊物删除；回执与接收游标在最终事务内提交。
6. A 只有收到成功确认后才推进该 peer 的发送确认游标。确认丢失时重发同一批次，由回执幂等返回成功。

该协商保证：即使 B 修改了一条 A 此后未再改动的同 ID 记录，A 仍会在下一次定向推送中重新发送自己的当前值，从而兑现“发送端胜出”。

## 5. 局域网协议与 LocalSend 式体验

网络层必须建立在同步内核之上，只负责发现、认证、协商和流式传输，不包含 SQLite 合并规则。

### 5.1 发现与交互

- 两台设备都打开“设备同步”页面并保持前台时，使用 TCP/UDP `53318` 主动组播 `239.255.70.80`、向有效 IPv4 网卡定向广播并立即单播回应；3 秒内无验证成功设备时扫描当前 `/24`。DNS-SD/NSD `_fprsync._tcp` 仅作为 IPv6 与兼容兜底。
- 发现信息只包含协议版本、临时可见设备名称/类型、端口和必要能力，不包含用户数据。
- UI 展示附近设备；用户手动选择发送目标，接收端明确接受后才开始传输。
- 接收端先显示同步预览：新增刊物、更新记录、删除记录、缺失大对象数量和预计字节数。
- 访客 Wi-Fi、VLAN、AP isolation、系统防火墙或移动系统权限可能阻止发现；界面应提供“无法找到设备”的诊断说明，未来可增加二维码/IP 直连作为受控回退。

### 5.2 配对、身份与传输安全

- 每台设备独立生成持久身份密钥和 TLS 证书；IP 地址和设备名称绝不作为身份。
- 首次配对在双方显示相同六位验证码，并由双方用户确认；确认后固定对端证书指纹和设备 ID。
- 后续连接使用 HTTPS 并校验已固定指纹；设备可在设置中撤销信任，撤销后必须重新配对。
- 逻辑数据使用版本化 JSON/NDJSON，可 gzip 压缩；`.fprpub` 使用限速、限长、可计算哈希的流式二进制上传。
- 所有输入视为不可信：限制请求体、记录数、文件大小、并发数和超时；拒绝路径穿越、哈希不符、未知高版本和不一致的重复批次。
- 初版不需要 WebSocket。请求/响应式 HTTPS 足以完成摘要、准备、上传、提交与确认；只有未来需要双向实时状态时再评估长连接。

建议的协议步骤为 `discover → pair/verify → summarize → prepare → upload missing blobs → apply → commit receipt`。可以借鉴 LocalSend 的产品体验和准备/确认流程，但不需要兼容 LocalSend 的文件传输协议。

## 6. Tauri Android 适配约束

跨平台边界固定如下：

- React renderer 只调用 `AppClient`，不得直接操作 socket、SQLite、Android API 或本地文件。
- `src/core` 保持纯 TypeScript，持有同步 DTO、校验、合并策略和平台端口。
- Electron/Windows 通过 Node 或 Rust 适配 SQLite、DNS-SD、HTTPS、文件 staging、证书和密钥存储。
- Tauri/Android 通过 commands/repository 暴露相同平台端口；需要原生能力时编写 Tauri 移动插件并在 Kotlin 侧调用 Android API。
- Android 主动发现位于 Kotlin 插件：页面期间持有 `MulticastLock` 并执行 UDP 广播/组播与受限 `/24` 扫描；`NsdManager` 保留为兜底。JavaScript 层不接触 socket。
- Android 当前 target SDK 36 在同步入口按需申请 `NEARBY_WIFI_DEVICES`，并持有仅页面活动期间使用的 multicast lock；面向后续强制本地网络权限的 target SDK 时，还必须声明并按需申请 `ACCESS_LOCAL_NETWORK`，或采用系统提供的受控设备选择机制。拒绝权限时本地阅读和便携备份仍可使用。
- 初版要求双方同步页面前台可见，不设计后台常驻发现。大文件传输若必须在切到后台后继续，应使用用户发起的数据传输任务，或符合 `connectedDevice` 用途及系统限制的前台服务，并提供持续通知和取消操作。
- Android 的具体文件目录、系统声音 ID、证书私钥和设备 ID 都是设备本地信息，不进入逻辑同步模型或便携备份。

Android 首个原型先验证 Tauri 外壳和本地产品闭环。数据库、持久目录和设备身份在平台基础阶段验证；NSD、HTTPS、批次和传输中断留到 Android 本地 MVP/Beta 之后的同步阶段。不要在只有 Electron 的情况下提前固化 Windows 专用网络接口。

阶段 F（`1.0.0-alpha.2`）当时只在 Android“数据与存储”中加入“跨设备同步”占位；该历史阶段不触发发现或传输。后续阶段 G 已用真实同步页替换占位，并复用平台无关的 Sync Model 与规范化刊物包，没有由 UI 重新定义数据协议；当前发送模型已顺序演进到 v3。

## 7. 分阶段实施路线

### 阶段一：同步数据基础（已完成，v0.8.0）

已交付：

- 建立版本化 Sync Model、稳定逻辑 DTO、`NewerWins`/`IncomingWins`/不可变并集策略。
- 新增刊物生命周期、逐词重置墓碑、合并式 revision 索引、peer 游标和批次回执。
- 为可同步写操作建立事务性变更登记；可再生、本机或敏感数据明确排除。
- 将阅读位置扩展为稳定内容锚点，并把需要跨平台的设置从本机设置中投影出来。
- 建立与 Sync Model 共用逻辑字段的便携备份；当前 format v3 与 Sync Model v3 共用规范化刊物包，并保留全量导入/导出入口及 format v2 恢复映射。
- 建立无网络的双库/三库 loopback 模拟，验证首次快照、增量、发送端胜出、墓碑、事件并集和转发。

阶段一当时的交付边界是 SQLite 与平台无关的数据内核、规范化刊物包、兼容向量及无网络测试；renderer 同步入口、IPC、socket、DNS-SD、HTTPS 与配对由后续阶段 G 接入。缺失刊物包协商现已实现；A→B→C 真实传播、网络中断和确认丢失仍属于尚未执行的端到端验收。

### 阶段二：Android 同步适配准备（代码已完成，端到端验收待执行）

交付内容：

- 已复用 Android 本地 MVP 的 Tauri commands/repository、正式 migration、持久目录和 Keystore 端口。
- 已增加 Android Rust 同步运行时、Kotlin `NsdManager` 插件、页面作用域发现/监听和共享 Sync API 客户端。
- 已用 TypeScript/Rust 共用向量分别冻结 Sync Model v2 与当前 v3 payload，并固定 Wire v2 发现报文、配对码、信任令牌与 NDJSON 哈希。
- Windows 与 Android 互相发现、配对、发送逻辑批次与规范化刊物包，以及权限拒绝、重启、传输中断与重试，尚待真实设备端到端执行。

Windows 正式应用继续使用 Electron，并作为同步对照端；阶段二不迁移 Windows 应用。只有协议适配验证无法在 Electron 对照端完成时，才建立一次性 Tauri Windows 测试壳，该测试壳不构成产品架构承诺。

当前门禁：两端对同一兼容向量生成一致结果、Rust/Kotlin/Android target 均可构建。未完成门禁：Android 重启后身份与数据、权限拒绝不影响本地能力，以及中断后无半导入刊物或错误回执的真实设备验证。

### 阶段三：Windows/Android 局域网同步产品化（实现完成，设备矩阵待执行）

交付内容：

- 已完成 Windows/Android 主动 UDP 发现、`/24` 扫描、DNS-SD/NSD 兜底、HTTPS 公开身份核验、证书固定、六位码双端确认、信任撤销和稳定设备列表。
- 已完成分页摘要、小型 prepare、NDJSON 流式批次、发送选择、接收确认、按本机实际状态计算的差异预览、缺失内容包上传、载荷级恢复、聚合进度、取消、错误状态和应用中不可取消保护。
- 网络层复用阶段一同步内核、revision、peer 游标、墓碑、规范化刊物包与幂等回执，不复制合并逻辑。
- Sync Model v3 已把分类、自定义刊名与归类关系拆成独立记录和墓碑，并在接收完成后统一刷新两端 UI；学习计划删除及进度重置会同步修复接收端设备本地队列。
- Windows 防火墙、AP isolation、不同 Android API/厂商网络栈的可操作诊断仍需在设备矩阵中核验和补充。

验收门槛保持不变：同一局域网前台使用可稳定完成首次和增量同步；错误设备不可静默接收；证书变化会阻断连接；取消、网络断开和确认丢失均可安全重试；防火墙/AP isolation/权限问题有可操作诊断。按当前安排，这组最终端到端验证暂不执行，因此阶段三不能仅凭构建成功标记为“设备验收完成”。

### 阶段四：多设备与传输韧性

交付内容：

- 完善三台及以上设备的游标治理、墓碑保留、revision 压缩和快照回退。
- 为大刊物包增加分块校验、断点续传、磁盘空间预检和 Android 前后台切换策略。
- 加入协议兼容矩阵、旧客户端降级提示、同步诊断日志和可导出的脱敏故障报告。

验收门槛：任意 A→B→C 顺序不丢失显式删除或不可变事件；离线设备重新加入后能从增量或快照安全恢复；日志压缩不破坏旧 peer；GB 级书库传输中断无需从零开始，且磁盘不足不会污染正式数据。

### 阶段五：可选云端对象存储/中继

交付内容：

- 在不改变本地优先模型的前提下，将按哈希寻址的规范化刊物包与加密逻辑批次放入用户选择的对象存储或中继。
- 复用同一 Sync Model、墓碑、revision、回执和兼容向量；局域网同步继续可独立使用。
- 账号、端到端加密、设备撤销、密钥轮换、配额和服务端不可信模型需单独完成安全设计。

验收门槛：断网时所有核心阅读/学习能力正常；服务端不能把“缺失对象”解释为用户删除；云端故障不损坏本地游标；新设备恢复必须显式授权且可验证完整性。未满足端到端加密和密钥恢复设计前，不发布云端同步。

## 8. 版本、兼容与发布纪律

- Sync Model、便携备份、局域网 wire protocol 和 SQLite schema 分别版本化，不因应用版本相同而假设格式相同。
- `formal-v1` migration 1、正式便携 format v1、Sync Model v1 和内容 ID v2 发布后不得改写；当前通过顺序 migration 2/3、便携 format v2/v3 与 Sync Model v2/v3 演进，旧基线和 v2 兼容向量继续冻结。
- 当前产品不读取便携 format v1，可读取 format v2 并在导入事务中建立 v3 细粒度书库记录；新导出使用 format v3。Sync Model v1 只保留冻结的内部接收映射，v2 记录保留映射能力，所有新摘要和批次使用 v3；Wire 仍为 v2。未知高版本必须明确拒绝，不做最佳猜测。
- SQLite 结构变化必须新增顺序迁移、旧版本升级测试和失败回滚测试，禁止改写已发布迁移。
- 内容 ID 算法版本独立保存。任何算法变化都必须保留旧 ID 的恢复/映射能力和跨平台兼容向量。
- 每个逻辑格式变更必须同时更新：便携导出、导入合并、同步批次、数据分类文档、幂等测试和恶意输入测试。
- 协议日志不得记录 API 密钥、证书私钥、原文全文或其他不必要的用户内容；错误信息也必须遵守此规则。
- 发布前至少覆盖两设备首传、无变化重传、双方分别修改、显式删除、旧数据复活防护、三设备传播、断线、磁盘不足、重复批次和高版本拒绝。

当前数据覆盖、自动化证据与 Windows ↔ Android 人工矩阵见[同步审计与验证清单](sync-validation.md)。
